# Co-RedTeam: LLMエージェントによるセキュリティ発見とエクスプロイトのオーケストレーション

## 論文技術解説

**論文情報:** arXiv:2602.02164v2 [cs.LG] — 2026年2月3日  
**著者:** Pengfei He (Michigan State University), Ash Fox, Lesly Miculicich, Stefan Friedli, Daniel Fabian, Burak Gokturk, Jiliang Tang, Chen-Yu Lee, Tomas Pfister, Long T. Le (Google Cloud AI Research / Google)

---

## 1. 背景と問題意識

レッドチーミングはサイバーセキュリティの根幹を成すプロアクティブな活動であり、CWE（Common Weakness Enumeration）やOWASP Top 10に体系化されるような脆弱性を、実攻撃に先んじて発見・検証・緩和する。しかし従来の手動レッドチーミングは、深い専門知識・反復的な仮説検証・大規模コードベースにわたる推論を要するため、スケーラビリティに根本的な課題を抱える。

LLMを用いた自動化が近年注目を集めるが、既存アプローチには以下の3つの構造的限界がある。

**限界1：脆弱な単発推論（Brittle Single-shot Reasoning）**  
単一LLMやシングルエージェントによる一発生成では、複雑な多段階推論・適応的攻撃計画・脆弱性空間の堅牢な探索が困難。CyBench、BountyBench、CyberGymといったベンチマークで成功率が10%以下に留まるケースが多い。

**限界2：実行に基づく検証の欠如（Lack of Execution-grounded Validation）**  
静的コード解析のみでは、環境固有の制約や不完全な仮定を検出できず、エクスプロイト生成の信頼性が低い。

**限界3：経験の再利用不能（Inability to Learn from Prior Attacks）**  
過去の攻撃軌跡から得られたパターンや戦略を蓄積・再利用する機構が存在しない。

## 2. Co-RedTeam アーキテクチャ全体像

Co-RedTeamは、人間のセキュリティ専門家によるレッドチーミングワークフローを模倣する、セキュリティ特化型マルチエージェントフレームワークである。以下の4つの能力を統合的に実装する。

| 能力 | 説明 | 実装手段 |
|------|------|----------|
| **Security Grounding** | セキュリティドメイン知識への接地 | CWE/OWASPドキュメントツール |
| **Code-aware Analysis** | コード構造に基づく精密な解析 | コードブラウジングツール群 |
| **Execution-driven Reasoning** | 実行フィードバックに基づく反復推論 | Docker隔離環境でのPlan-Execute-Evaluate閉ループ |
| **Experience Accumulation** | 経験の蓄積と再利用 | 3層長期メモリ |

## 4. Orchestrator（オーケストレータ）の詳細設計

Orchestratorはシステム全体の中央制御器として、以下の責務を担う。

**エージェント初期化とロール別ツール割当：** Discovery段階のエージェントにはコードブラウジングツールと脆弱性ドキュメントツールを、Exploitation段階のエージェントにはDocker隔離環境内のrun-bash/run-pythonインターフェースを割り当てる。エージェントインスタンスとツールハンドルはキャッシュされ、ステージ間で一貫したコーディネーションを保証する。

**動的実行パス決定：** ユーザ入力のコードパスと脆弱性記述（オプション）を検証し、十分な仮説が得られている場合はStage IIに直行、そうでなければStage Iから開始する。

**状態監視とスケジューリング：** 中間条件の充足に基づきエージェント間のインタラクションを進行させる。脆弱性が実行を通じて再現された場合、追加探索を停止しレポート生成に遷移する。この設計はGoogle Co-Scientistのスーパーバイザーエージェントと同様の思想に基づく。

## 5. Stage I: Vulnerability Discovery（脆弱性発見）

### 5.1 Analysis Agent（解析エージェント）

Analysis Agentの設計思想は、LLM単独ではコードベースの脆弱性を信頼性をもって識別できないという実証的知見に基づく。プログラム構造とセキュリティドメイン知識の双方に推論を接地させることが鍵となる。

**コードブラウジングツール群：**  
`get_whole_file_structure_tool`、`list_directory_tool`、`read_file_tool`、`get_snippet_tool`、`read_readme_tool`等を通じて、ファイル階層・ドキュメント・エントリポイント（ルート、API）・設定ファイル・詳細コードスニペットを体系的に探索する。局所的パターンマッチングではなく、プログラム構造とデータフローのグローバルな理解を構築する。

**セキュリティ知識ツール：**  
CWE/OWASPから蒸留された構造化セキュリティ知識ソースに接続。`get_vulnerability_summary`と`query_vulnerability_docs`を通じて、疑わしいコード断片を既知の脆弱性クラスとエクスプロイトメカニズムのレンズで解釈する。

**分析戦略（プロンプト内で指示）：**

| 戦略 | 目的 | 手法 |
|------|------|------|
| Taint Analysis（汚染解析） | インジェクション欠陥検出 | エントリポイントからDangerous Sinkへの追跡 |
| Trust Boundary Mapping | 認証・認可バイパス | 信頼境界での検証有無の確認 |
| Configuration & Dependency Audit | インフラ欠陥 | Dockerfile、設定ファイル、依存関係の監査 |
| Business Logic Tracing | IDOR、ワークフローバイパス | 多段階ユーザアクションのサーバ側検証追跡 |

**エビデンスチェーン構築：** 各候補脆弱性に対し、入力ソース（信頼されない入力の入口）、脆弱なシンク（危険な処理が行われる箇所）、実行コンテキスト（既存バリデーション/サニタイズが不十分な理由）を明示的に特定する。出力は、標準化された脆弱性クラス（CWE形式）、簡潔な記述、ファイル・行レベルの証拠、影響の根拠で注釈付けされた構造化リストである。

### 5.2 Critique Agent（批評エージェント）

独立した検証者として機能し、Analysis Agentの出力をレビューする。

**リスクレベル評価：**  
Critical（即時対応）、High（日単位の修復）、Medium（標準的修復）、Low（リソースがある場合の修復）、Informationalの5段階。

**レビューステータス：**  
Approved（承認）、Rejected（却下）、Needs Refinement（要改善）のいずれかを、具体的フィードバックとともに付与。説得力のある証拠を欠く候補やlow-impactの候補は却下、もっともらしいが裏付け不足の仮説は改善要求される。

### 5.3 Analysis–Critique反復ループ

```
Analysis Agent ──(脆弱性ドラフト)──→ Critique Agent
     ↑                                       │
     │         ←──(フィードバック)──          │
     │   [Rejected/Needs Refinement]          │
     │   コードベース再調査、証拠強化          │
     │   or 候補棄却                           │
     └────────────────────────────────────────┘
                     ↓ [安定した検証済みセット]
              Stage II へ移行（最大3反復）
```

この反復により、偽陽性の低減とロバスト性の向上が実現される。最終出力は、明示的な証拠と評価済みリスクレベルに裏付けられた、高信頼の脆弱性候補のキュレーション済みセットである。

## 6. Stage II: Iterative Exploitation（反復エクスプロイト）

Stage IIは、静的コード推論では到達し得ない「実行を通じた精密な検証」を担う段階である。単発エクスプロイト生成ではなく、実行フィードバックに導かれた構造化探索プロセスとして設計されている。

### 6.1 Planner Agent（計画エージェント）

**Exploit Plan（エクスプロイト計画）：** 明示的で検査可能なステップ列としてエクスプロイトを分解する。各ステップはgoal、action、status（planned / done / blocked）で構成され、進捗と失敗の透過的追跡を可能にする。

**Grounding Phase（接地フェーズ）：** 人間のセキュリティ専門家が不慣れな対象に取り組む際のプロセスを模倣する。

1. 脆弱性記述と証拠チェーンの解釈
2. 脆弱性ドキュメントからの関連セキュリティ知識の取得
3. コードベースのスキャンによる技術スタックと攻撃面の理解
4. 長期メモリからの過去の成功戦略/技術パターンの参照

**フィードバック駆動の計画改訂：** 各実行後、Plannerは試行したステップのステータスを更新し、失敗をblockedとしてマークし、必要に応じて修正アクション（ファイルパス調整、ペイロード切替、代替コマンド試行等）を挿入する。さらに、新たに観測された証拠に照らして将来の計画ステップも見直し、仮定が実行フィードバックにより無効化されたステップを修正・破棄する。これにより、古い計画に盲目的に従ったり、無効なアクションを繰り返し実行したりすることを防止する。

### 6.2 Validation Agent（検証エージェント）

セキュリティ設定では、不正なコマンドや安全でないアクションが実行を無効化し得るため、安全性と整合性のゲートとして機能する。提案されたアクションが整形式か、構文的に正しいか、意図した目標と整合するか、観測されたシステム状態と互換性があるかを検証する。無効なアクションはPlannerに差し戻される。

### 6.3 Execution Agent（実行エージェント）

検証済みアクションをDocker隔離環境内で実行する。ターゲットシステムとのリアルなインタラクションを保証しつつ、元のコードベースへの意図しない変更を防止する。実行結果には構造化されたステータスシグナル、生出力、エラーメッセージが含まれる。

### 6.4 Evaluation Agent（評価エージェント）

低レベルの実行トレースを高レベルの推論シグナルに変換する役割を担う。

- 実行が意図した目標を達成したかの判定
- 逸脱や予期しない挙動の強調
- 環境・設定エラーの特定
- 次のステップの具体的提案生成

### 6.5 Exploitation閉ループフロー

```
                    ┌──────────────────┐
                    │  Planner Agent   │
                    │  (計画策定/改訂)  │
                    └────────┬─────────┘
                             │ アクション提案
                             ▼
                    ┌──────────────────┐
                    │ Validation Agent │
                    │ (整合性チェック)  │
                    └────────┬─────────┘
                             │ 検証済みアクション
                    ┌────────┴─────────┐
                    │ 無効 → Plannerへ │
                    │        差し戻し   │
                    └──────────────────┘
                             │ 有効
                             ▼
                    ┌──────────────────┐
                    │ Execution Agent  │
                    │ (Docker隔離環境)  │
                    └────────┬─────────┘
                             │ 実行結果
                             ▼
                    ┌──────────────────┐
                    │ Evaluation Agent │
                    │ (結果評価)        │
                    └────────┬─────────┘
                             │
                   ┌─────────┴──────────┐
                   │                    │
              成功 / 反復上限      フィードバック
                   │                    │
                   ▼                    ▼
              最終レポート        Plannerへ戻る
              生成               (計画改訂)
```

デフォルトの最大反復数は20だが、実際には13〜18反復で終了する傾向がある。Gemini-3-Proはより早く（約13反復）ピーク性能に到達し、Gemini-2.5-Proは約17反復まで改善が続く。

## 7. Long-term Memory（長期メモリ）の3層設計

人間の専門家が経験を蓄積して成長するプロセスを模倣する。脆弱性発見には抽象的パターン認識が、エクスプロイトには戦略的計画と低レベル技術実行の双方が必要であり、単一の均質なメモリ表現では不十分である。この観察に基づき、3層に分離する。

### 層1: Vulnerability Pattern Memory（脆弱性パターン記憶）

検証済み脆弱性提案とエクスプロイト結果から蒸留された確認済み脆弱性スキーマを格納する。各パターンは、観察可能な症状 → 脆弱性仮説 → 確認テストの進行を記録し、確認を妨げた一般的な偽のリード（false leads）も含む。

例：一見無害なURL取得関数が特定の設定フラグと組み合わさった場合にのみエクスプロイト可能になるパターン。異なるコードベース間での再発脆弱性構造の迅速な認識を支援する。

### 層2: Strategy Memory（戦略記憶）

完了したExploit Planから抽象化された高レベルのエクスプロイト戦略を格納する。ターゲット間で転移可能な一般化可能な教訓を合成する。

- 成功戦略の例：「ペイロード作成前に設定分析を優先する」
- 失敗パターンの例：「実行コンテキストの理解なしのブラインドファジングはデッドエンドに至る」

類似の脆弱性クラスに対するエクスプロイトワークフロー（例：異なるWebフレームワーク間のXSSエクスプロイト戦略）として一般化される。

### 層3: Technical Action Memory（技術アクション記憶）

実行ログとExploit Planから抽出された具体的な低レベルアクション（コマンド、スクリプト、ツール呼び出し）を記録する。

- 成功時：再利用可能な「how-to」スニペットや技術的トリックとして蒸留（例：SSRFの到達性テスト用の動作するコマンド）
- 失敗時：関連するピットフォールと修正調整を格納（例：誤ったファイルパスの仮定とその修正）

### メモリの実装詳細

- **メモリ合成：** LLMベースの抽出（gemini-2.5-pro使用）で、研究計画・実行トレース・評価フィードバックから自動合成
- **シグナル源：** Evaluation AgentとOrchestratorが、軌跡が保存すべき成功プラクティスか回避すべき失敗教訓かを判定
- **検索：** エンベディングベースの類似度検索（gemini-embedding-001モデル、クエリあたりtop-3取得）
- **コールドスタート回避：** 確立されたセキュリティデータベースと人間専門家の経験から蒸留されたキュレーション済みアイテムで初期化

## 8. 実装詳細

**エージェント構築基盤：** Google ADK（Agent Development Kit）フレームワーク

**入出力スキーマ：** 厳格なinput/output schemaを採用し、エージェントの入出力のフォーマットと内容を規制

**実行環境：** コードブラウジングツールとExecution AgentはDocker隔離コンテナ内で動作

**バックボーンLLM：** フレームワーク内の全エージェントは同一のバックボーンLLMで実体化（システム設計の効果を分離するため）

**Stage Iの反復上限：** 脆弱性提案の改善に最大3反復

**Stage IIの反復上限：** エクスプロイトループはデフォルト20反復

## 9. 評価ベンチマークと実験結果

### 9.1 ベンチマーク概要

| ベンチマーク | 特徴 | タスク種別 |
|-------------|------|-----------|
| **CyBench** | CTFベース。LLMエージェントのセキュリティ脅威発見・緩和能力を評価 | Exploitation |
| **BountyBench** | 実世界の攻撃・防御サイバー能力を対象。25システム、40バグバウンティ | Detect + Exploit |
| **CyberGym** | 大規模かつ現実的。実行可能なPoC生成による脆弱性再現を重視 | Exploitation |

### 9.2 ベースライン

- **Vanilla Model：** ツール使用・実行フィードバック・構造化計画なしの最小ベースライン
- **OpenHands：** ソフトウェアエンジニアリング向け汎用コーディングエージェント（セキュリティ非特化）
- **C-Agent：** CyBench提供。実行フィードバックを推論ループに組み込む
- **VulTrail：** 模擬法廷パラダイムによる脆弱性検出（LLMエージェント間の構造化ディベート）
- **RepoAudit：** リポジトリレベルのコード監査用自律LLMエージェント

### 9.3 主要結果（Gemini-3-Pro使用時）

| 手法 | CyBench | BountyBench (Exploit) | BountyBench (Detect) | CyberGym |
|------|---------|----------------------|---------------------|----------|
| Vanilla | 18.5% | 17.5% | 0.0% | 12.1% |
| OpenHands | 45.2% | 45.0% | 5.0% | 20.2% |
| C-Agent | 47.8% | 47.5% | 5.0% | 21.5% |
| VulTrail | N/A | 10.0% | 0.0% | 5.6% |
| RepoAudit | N/A | 25.0% | 2.5% | 18.3% |
| **Co-RedTeam** | **63.7%** | **65.0%** | **20.0%** | **37.3%** |

全ベンチマーク・全バックボーンモデルにおいてCo-RedTeamが最強の性能を達成。特にVulTrailとRepoAuditは実行フィードバックを推論ループに組み込まないため、エクスプロイトタスクで顕著に弱い。

### 9.4 アブレーション結果（Gemini-2.5-Pro使用時）

| 除去コンポーネント | CyBench | BountyBench (Exploit) | BountyBench (Detect) | CyberGym |
|-------------------|---------|----------------------|---------------------|----------|
| Full Co-RedTeam | 59.1% | 60.0% | 12.5% | 31.5% |
| No Execution | 17.5% (▼41.6pt) | 12.5% (▼47.5pt) | 0.0% (▼12.5pt) | 14.3% (▼17.2pt) |
| No Memory | 50.0% (▼9.1pt) | 40.0% (▼20.0pt) | 7.5% (▼5.0pt) | 22.6% (▼8.9pt) |
| No Code Browser | 47.5% (▼11.6pt) | 42.5% (▼17.5pt) | 7.5% (▼5.0pt) | 27.9% (▼3.6pt) |
| No Validation | 52.3% (▼6.8pt) | 42.5% (▼17.5pt) | 7.5% (▼5.0pt) | 28.3% (▼3.2pt) |
| No Vul-doc | 55.2% (▼3.9pt) | 52.5% (▼7.5pt) | 10.0% (▼2.5pt) | 30.2% (▼1.3pt) |
| No Critique | N/A | N/A | 10.0% (▼2.5pt) | N/A |

**最も影響が大きいのは実行フィードバックの除去**で、CyBenchでASRが59.1%→17.5%に低下。次いで長期メモリの除去がCyberGymで大きな影響（▼8.9pt）。コンポーネント単独ではなく、計画・実行・検証・批評・メモリの相乗的統合が強力な性能を生むことを示す。

## 10. メモリ進化分析

CyberGymにおけるGemini-2.5-Proでの4構成比較：

| 構成 | 特徴 | 挙動 |
|------|------|------|
| **No Memory** | 長期メモリなし | 初期から低い性能、プラトー |
| **Static Memory** | キュレーション済みメモリ固定、更新なし | 初期性能は改善するがプラトー |
| **Cold Start (Evolving)** | 空メモリから開始、継続的書き込み | 当初は低いが徐々にWarm Startに追いつく |
| **Warm Start (Evolving)** | キュレーション済みメモリ + 継続的更新 | 最強。初期の素早い立ち上がりと継続的改善の双方 |

この結果は、メモリの2つの補完的効果を示す：初期化効果（事前知識による探索ガイダンス）と進化効果（経験に基づく継続的改善）。Cold Start (Evolving)がWarm Start変種に徐々に追いつく点は、エージェントが経験から自律的に有効な戦略を獲得可能であることを実証している。

## 11. 脆弱性発見の精度分析

BountyBench（Gemini-2.5-Pro）でのPrecision/Recall：

| 手法 | Precision | Recall |
|------|-----------|--------|
| Vanilla | 0.000 | 0.000 |
| OpenHands | 0.000 | 0.000 |
| C-Agent | 0.024 | 0.025 |

Co-RedTeamのPrecision 14.3%はC-Agentの約5.95倍。Co-RedTeamは通常0〜2個の脆弱性を報告するが、その信頼性が格段に高いことを示す。

## 13. 技術的意義と考察

**エクスプロイト成功率60%超の意味：** CyBench/BountyBench/CyberGymは、大規模な現実的コードベースを対象とするベンチマークであり、従来の汎用エージェントでは10%以下に留まることも多い。60%超の達成は、セキュリティ特化のマルチエージェント設計が汎用設計と本質的に異なる性能域に到達し得ることを実証する。

**閉ループ設計の不可欠性：** アブレーションで実行フィードバック除去時に最大41.6ptの性能低下が生じることは、静的解析のみのアプローチの限界を定量的に裏付ける。脆弱性は実行を通じてのみ精密に検証可能であるという原則が、数値として明確に示された。

**経験蓄積の効果：** メモリ進化分析は、エージェントが逐次的タスク処理を通じて自律的に戦略を獲得・改善できることを示す。これはHexStrikeのような実践的AIペンテストフレームワーク開発においても、類似の3層メモリアーキテクチャ設計の妥当性を支持する知見である。

**精度（Precision）重視の設計哲学：** Co-RedTeamが報告する脆弱性は少数（0〜2個）だが高精度である。これは「大量の候補を出して人間がフィルタする」アプローチとは対照的であり、人間レビューのボトルネックを考慮した実践的設計と言える。

## 14. 関連研究における位置づけ

Co-RedTeamは、以下の研究系譜の交差点に位置する。

**LLMs for Cybersecurity：** LLMによる脆弱性検出・エクスプロイト・修復（Xu et al., 2025; Zhang et al., 2025b）。Chain-of-Thoughtプロンプティングによる性能改善（Nong et al., 2024）が報告されるが、複雑な推論での限界が実証的に示されている（Ding et al., 2024; Steenhoek et al., 2024）。

**Agentic Systems for Security：** 単一エージェントの反復的ワークフロー（Ding et al., 2024; Guo et al., 2025; Zhang et al., 2024）、模擬法廷パラダイム（VulTrail / Widyasari et al., 2025）、協調的エクスプロイト（Fang et al., 2024）。ただし既存システムは大規模現実的コードベースでの成功率が低い。

**Co-RedTeamの差別化：** セキュリティドメイン知識への接地、コード認識型分析、実行駆動の反復推論、3層長期メモリの4要素を統合的に実装した初のフレームワーク。

---

## 15. まとめ

Co-RedTeamは、LLMベースのレッドチーミングが抱える3つの構造的限界（脆弱な単発推論、実行に基づく検証の欠如、経験再利用の不能）に対し、セキュリティ特化のマルチエージェント設計で包括的に対処するフレームワークである。Discovery（分析・批評の反復ループ）とExploitation（計画・検証・実行・評価の閉ループ）の2段階構造に3層長期メモリを統合し、60%超のエクスプロイト成功率と10%超の検出精度改善を実現した。
